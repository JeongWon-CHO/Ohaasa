# 방송별 일일 운세 수집 (#74)

TV 버튼에서 고고별자리·메자마시의 최신 저장 운세를 직접 조회하기 위한 별도 수집 경로다.
기존 프로덕션 `horoscopes` 저장, `resolved_horoscopes` 선택 규칙, 알림 발송 경로는 유지한다.

## 데이터 경로

| 용도                          | 저장/조회 대상                                                              |
| ----------------------------- | --------------------------------------------------------------------------- |
| 기존 메인 운세·주말 대체·알림 | 기존 수집기 → `horoscopes` / `mezamashi_horoscopes` → `resolved_horoscopes` |
| 방송별 고고 조회              | 새 수집기 → `gogo_horoscopes`                                               |
| 방송별 메자마시 조회          | 새 수집기 → 기존 `mezamashi_horoscopes`                                     |

평일 오하아사 행에 고고 색상·점수를 병합하는 기존 동작도 유지한다.
고고 전용 테이블에는 고고의 실제 순위·본문·색상·아이템·점수와 번역을 저장한다.
중복 저장을 허용해 기존 앱과 독립적으로 제공한다. 기존 혼합 행에서 고고 본문/순위를 추정하지 않는다.
새 테이블의 자동 과거 데이터 이관은 하지 않는다. 최초 예약 수집 전에는 고고 목록이 비어 있을 수 있다.

기존 앱은 기존 경로를 계속 읽는다. 새 테이블을 읽는 클라이언트 코드는 별도의 앱 출시에 포함해야 한다.

## 수집 동작

- 핸들러: `backend/src/lambda/broadcast-crawl-handler.ts`
- 평일·주말 모두 두 방송을 독립적으로 시도한다. 한쪽 실패가 다른 쪽 수집을 취소하지 않는다.
- 원문 날짜가 JST/KST 오늘과 다르면 저장하지 않는다. 일요일에 토요일 운세가 남아 있어도 날짜를 바꾸지 않는다.
- 12개 별자리·순위·필수 본문/항목·점수를 검증한 뒤 날짜별 12행을 한 번에 upsert한다.
- 원문이 같은 필드의 유효한 번역을 재사용한다. 번역 실패는 null로 보존하고 이후 예약에서 재시도한다.
- 고고 기존 번역 조회 실패 시 저장을 중단해 번역을 덮어쓰지 않는다.
- 고고 저장은 `gogo_horoscopes`에만 수행한다. 새 수집기는 `horoscopes`나 알림 테이블을 수정하지 않는다.
- 메자마시는 기존 수집 함수를 재사용한다. 주말에는 기존 대체 운세 경로도 같은 테이블을 사용할 수 있다.
- 신규 Lambda는 발송기·Edge Function·Step Functions를 호출하지 않는다. 메자마시 저장 자료는 기존 대체 규칙에 따라 기존 알림에서 사용될 수 있다.
- 로그는 방송·날짜·상태·건수만 기록한다. 일부 실패는 `failed`로 기록하고, 양쪽 모두 예외로 실패하면 Lambda 오류로 처리한다.

## AWS 분리

`infra/aws/broadcast-template.yaml`을 **별도 스택** `ohaasa-broadcast-collector`로 배포한다.
기존 `ohaasa-scheduler` 스택에 이 템플릿을 배포하면 안 된다.

- 새 예약: 매일 한국 시간 **06:05, 06:25, 06:45, 07:05, 07:25, 07:45** (`cron(5,25,45 6-7 * * ? *)`).
- 메자마시 공식 페이지의 평일 웹 갱신 안내는 07:00이다. 앞선 06시대 예약만으로는 그날 갱신본을 놓칠 수 있어 07시대 확인을 포함한다. 토요일 갱신 시각은 별도 관측이 필요하다.
- `BroadcastScheduleState`는 기본 **DISABLED**. 운영 적용을 명시적으로 요청받기 전 활성화하지 않는다.
- 제한 시간 900초로 정상 예약 실행은 다음 20분 슬롯 전에 종료된다. 지연 전달 시 중첩될 수 있으며 날짜·별자리 PK로 저장 중복을 처리한다.
- 현재 계정의 동시 실행 한도는 10이라 AWS가 예약 동시 실행 1 설정을 허용하지 않는다. 새 함수는 공유 동시 실행 용량을 사용하고 기존 계정 한도는 변경하지 않는다.
- 하루 여섯 번의 고정 예약을 사용하며 Scheduler·Lambda 자체 추가 재시도는 0회다.
- Lambda 비동기 실패와 Scheduler 전달 실패는 새 전용 SQS DLQ로 보낸다. 로그는 30일 유지한다.
- 일부 실패/오래된 자료는 Lambda 오류가 아닐 수 있으므로 예약 실행 확인 시 방송별 결과 로그와 실제 저장 날짜를 함께 본다.
- 기존 Secrets Manager의 백엔드 설정을 파라미터 ARN으로 참조한다. 키 값을 설정 파일/로그에 기록하지 않는다.

## 적용 순서

아래는 이후 별도 승인된 운영 적용 절차이며 이 코드 변경만으로 실행되지 않는다.

1. 새 SQL `supabase/migrations/20261027000000_gogo_horoscopes.sql`을 검토·적용하고 RLS/읽기 권한을 확인한다.
2. 최신 소스로 새 SAM 템플릿을 빌드한다. 기존 `.aws-sam` 아티팩트는 재사용하지 않는다.
3. 별도 스택의 변경 세트를 확인하고 **예약 비활성화** 상태로 배포한다. 기존 스택 리소스가 포함되지 않아야 한다.
4. 새 테이블을 읽는 앱 변경을 검증한다. 앱 출시 시 대상 `app.config.js`의 버전을 올린다.
5. 별도 요청 후 새 스택의 `BroadcastScheduleState`를 `ENABLED`로 적용한다.
6. 다음 자연 예약 실행 후 DB의 방송별 날짜·12개 별자리·번역 상태와 CloudWatch 결과/DLQ를 읽기 전용으로 확인한다.

기존 수집 Lambda·새 수집 Lambda·알림 발송기·Step Functions를 테스트 목적으로 수동 실행하지 않는다.
알림 검증은 `dry_run: true`만 허용하며 실제 푸시는 보내지 않는다.
현재 운영 `ohaasa-scheduler` 수집 코드는 과거 직접 교체 이력이 있으므로 향후 그 스택을 배포할 때도 #72 이후 변경을 포함한 최신 소스를 다시 빌드해야 한다.

## 비활성화/롤백
